What Jev is

TypeSafe AI calls Jev a System One model, after Kahneman's fast thinking. You hand it state, meaning whatever your program already holds: a support ticket, a file, the last six turns of a conversation. Alongside the state you send a set of typed questions. Jev returns one answer per question, each with a probability distribution behind it. It writes no text and calls no tools.

The company's own line for it: "a frontier-intelligence function call: unstructured state in, typed probabilistic decisions out." That framing matters more than the benchmark. Jev decides. It leaves the writing to something else.

70–500 msEnd to end. Most calls land near 100 ms, per TypeSafe.
$0.042Per million input tokens. Output tokens cost nothing.
0%Malformed answers, by construction rather than by measurement.
12.2×Cheaper than 13 separate calls, on a 53,777-character document.

Vendor figures from the TypeSafe launch post and docs, September 2026. Nobody outside the company has reproduced the latency yet.

A frontier LLM asked to classify a support ticket loads the prompt and generates one token at a time, feeding each token back in before it picks the next. That loop is what autoregressive means. The model stops, and hands you a string you then parse and validate. TypeSafe measured those round trips at 3 to 329 seconds. Jev loads the same state once and reads out every answer in parallel.

How it answers ten questions in the time an LLM writes one word

Three design choices do the work.

The architecture is non-autoregressive. Jev produces all its outputs from a single pass rather than feeding each token back in. TypeSafe describes it as parallel sampling that is hardware-aware. Jev scores every question in a request against the same state, and no question sees another's answer, so one answer cannot poison the next. TypeSafe says it found no batching penalty past normal sampling noise.

You fix the output space in advance. You declare the options before the call. The model picks among them and reports how the probability mass fell. A malformed answer has nowhere to live, which is why the 0% type-error rate is structural. That claim says nothing about whether the answer is right.

Training targeted calibration, which means the probability the model states matches how often that answer turns out right. TypeSafe trained Jev with Reinforcement Learning for Calibrated Decisions, which rewards exactly that. Over many answers, the ones marked 0.9 should be right about nine times in ten. That property makes confidence usable as a gate in code: confidence is the share of the probability mass sitting on the answer the model picked. Test it on your own data before you trust it in production.

THE OPEN REPRODUCTION TELLS YOU MORE THAN THE BLOG POST.

openjev-sglang rebuilds the interface on open weights with a one-token readout: read the state once, append a per-question suffix, then take the model's own scores for the answer labels (its log-probabilities) and renormalize them over those labels alone. Labels are A–Z and verified single-token pairs such as AA, so every answer reads out in exactly one token. Jev may not work this way inside. openjev is still the cheapest way to get the same call shape on a model you host, and it runs on SGLang, an open-source inference server.

The three primitives

Every question you can ask is one of three types. You mix them in one request. Each answer carries its probability distribution and its confidence.

TypeAsksReturns
Noul Is this statement true of the state? .noul, a probability from 0 to 1. No separate confidence field, because the number is the confidence.
Choice Which of these options fits? Up to 255 of them. .choice, .probabilities over every option, .confidence.
Score Where on this ordered rubric does it sit? .score, which lands between levels (1.035 is a real answer), .probabilities, .confidence. 
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()          # reads TYPESAFE_API_KEY, defaults to jev-latest

response = client.system_one(
    state={
        "ticket": {
            "subject": "Duplicate charge",
            "messages": [
                {"from": "customer",
                 "text": "I was charged twice for order A-104. Please refund the duplicate."},
            ],
        },
    },
    questions={
        "department": Choice(
            instructions="Which team should handle this",
            criteria={"billing": "Payment issues",
                      "technical": "Bugs or integration problems",
                      "sales": "Pricing questions"},
        ),
        "frustration": Score(
            instructions="How frustrated the customer appears",
            criteria=["Calm", "Frustrated but civil", "Very angry"],
        ),
        "refund_requested": Noul(
            instructions="The customer is explicitly asking for a refund",
        ),
    },
)

dept = response.answers["department"]
print(dept.choice, dept.confidence)

Two rules govern how you write the questions. Keep each one atomic, so it asks about one thing. Break a compound judgment into parts and combine them in your own code, where you can see the weights and change them without retraining anything.

The request and the response

One endpoint: POST https://api.typesafe.ai/v1/systemone. The body holds state, model and questions. The response holds model, answers keyed by your question ids, and usage.

State can be a string, an object, or an array. Use an object. Named fields tell the model what each part is. They also let you diff one state against another once you log every call.

Five patterns that hold up

1. Fan out

Ask everything you might want in one request. TypeSafe batched 13 questions against a 53,777-character document and measured it at 12.2× cheaper and 10× faster than 13 separate calls, because Jev reads the state once. Adding a question adds its own tokens and close to no time.

2. Gate on confidence, and set a different gate per action

The cost of being wrong differs by action, so one threshold across a system is wrong for most of it.

action = response.answers["intent"]

if action.confidence < 0.5:
    route_to_human(user_message)             # genuinely unsure

elif action.choice == "check_balance":
    show_balance(account_id)                 # read-only, low bar

elif action.choice == "approve_transfer":
    if action.confidence > 0.85:             # money moves, high bar
        approve_transfer(account_id)
    else:
        ask_user_to_confirm("Approve this transfer?")

3. Composite scoring

Split a judgment into dimensions, ask each on its own, and weight them in code.

composite = (
    0.40 * (response.answers["python_depth"].score / 4) +
    0.25 * (response.answers["team_leadership"].score / 4) +
    0.35 * (response.answers["system_design"].score / 4)
)

The weights live in your repo, under review, in a diff. Changing how much system design counts takes a pull request rather than a prompt rewrite.

4. Cascade

Jev routes. Plain code handles the easy cases and a frontier model takes the rest.

if intent.confidence < 0.5:
    return route_to_human(message)

if intent.choice == "order_status":
    return lookup_order(message)             # pure code, no model
elif intent.choice == "complaint":
    if complexity.score > 1:
        return route_to_human(message)
    return handle_with_llm(message, SPECIALIST)

5. Retrieve, then judge

Filter in code first and send the fields the question needs. Accuracy falls as you pad the state with material that has nothing to do with the question, and you pay for the padding.

What it gets wrong

TypeSafe publishes the failure modes, which is more than most model cards do. Weigh them before you wire Jev into a decision path.

  • It cannot count. Characters in a word, occurrences of a term, items in a list: all unreliable.
  • Date and number comparisons fail. Which of two dates came first, how far apart they are, whether two hex colors are close. Do this in Python.
  • It reads literally. Negations and scoping words land at face value, so "this is not a refund request" can score high on a refund question.
  • Padding costs accuracy. State you did not need for the question drags the answer down.
  • User-controlled text steers it. Content written to argue for its own classification moves the answer. Treat state built from user input the way you treat a prompt: untrusted.
  • No text, ever. No explanations, no code, no summaries. It takes no images, audio or video.
  • Accuracy is 67.8% on TypeSafe's own benchmark, scored against consensus labels from GPT-6 and Claude. TypeSafe ran that evaluation itself, so reproduce it on your own data before you commit to a gate.

PIN THE VERSION. Both SDKs default to jev-latest. The moment you tune a threshold against measured behavior, pin the model ("jev-1.13.0"), or a silent upgrade will move your answers under a gate you calibrated last month.

Build idea 1: mine Claude Code transcripts into a decision dataset

Your idea, worked out

Claude Code already records every decision it made and what happened next. That is a labeled dataset sitting on disk, and nobody is using it. Jev turns it into a counterfactual one, a record of what a second opinion would have done at each step. At each point where the agent picked a tool, ask Jev what it would have picked. Then read the rest of the transcript for how the agent's choice turned out.

What the files hold

On this Windows box the transcripts live at %USERPROFILE%\.claude\projects\<slug>\<session-uuid>.jsonl, where the slug is the working directory with separators turned into dashes: c--Users-aroraai-Downloads-my-work-SFDC. One session file there runs to 3.76 MB. Sampling its first 400 lines gives the record shapes:

RecordKeysCount in 400 lines
assistant turnparentUuid, isSidechain, message, type, uuid, timestamp, effort, cwd, sessionId, version, gitBranch136
tool resultthe above plus promptId, toolUseResult, sourceToolAssistantUUID58
user promptthe above plus permissionMode, origin, promptSource10
attachmentattachment in place of message95
bookkeepingaiTitle, lastPrompt/leafUuid, operation, file snapshots101

Inside an assistant record, message.content holds blocks. A tool_use block carries type, id, name, input. The matching result arrives in a later record as a tool_result block, with the raw payload beside it in toolUseResult and a back-pointer in sourceToolAssistantUUID. message.usage gives input, output, cache-read and cache-creation tokens per turn, so every decision point carries its own price.

The extractor

import json, pathlib
from collections import deque

ROOT = pathlib.Path.home() / ".claude" / "projects"
WINDOW = 6          # turns of context to carry into the state

def records(path):
    with path.open(encoding="utf-8") as fh:
        for line in fh:
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError:
                continue          # snapshots and partial writes

def text_of(msg):
    out = []
    for block in msg.get("content") or []:
        if isinstance(block, dict) and block.get("type") == "text":
            out.append(block["text"])
    return "\n".join(out)

def decision_points(path):
    """Yield one dict per tool_use block, with context before and result after."""
    context = deque(maxlen=WINDOW)
    pending, rows = {}, []

    for rec in records(path):
        kind = rec.get("type")
        msg = rec.get("message") or {}

        if kind == "user" and isinstance(msg.get("content"), str):
            context.append({"role": "user", "text": msg["content"]})

        if kind == "assistant":
            said = text_of(msg)
            if said:
                context.append({"role": "assistant", "text": said})
            for block in msg.get("content") or []:
                if block.get("type") != "tool_use":
                    continue
                row = {
                    "session": rec.get("sessionId"),
                    "uuid": rec.get("uuid"),
                    "cwd": rec.get("cwd"),
                    "branch": rec.get("gitBranch"),
                    "ts": rec.get("timestamp"),
                    "context": list(context),
                    "tool": block["name"],
                    "input": block.get("input", {}),
                    "tokens": (msg.get("usage") or {}).get("output_tokens"),
                }
                pending[block["id"]] = row
                rows.append(row)

        for block in (msg.get("content") or []) if isinstance(msg.get("content"), list) else []:
            if isinstance(block, dict) and block.get("type") == "tool_result":
                row = pending.pop(block.get("tool_use_id"), None)
                if row is not None:
                    row["result"] = rec.get("toolUseResult")
                    row["is_error"] = bool(block.get("is_error"))

    return rows

The labels, taken from the transcript itself

INTERRUPT = "[Request interrupted"

def label(row, later_rows):
    if row.get("is_error"):
        return "failed"
    for nxt in later_rows[:3]:
        for turn in nxt["context"]:
            if turn["role"] == "user" and INTERRUPT in turn["text"]:
                return "interrupted"
    path = (row["input"] or {}).get("file_path")
    if path and row["tool"] in {"Edit", "Write"}:
        for nxt in later_rows[:6]:
            if nxt["tool"] in {"Edit", "Write"} and (nxt["input"] or {}).get("file_path") == path:
                return "reworked"          # it came back to the same file
    return "clean"

Those four labels are crude. Each one comes from something that happened in the session rather than from a model's opinion. failed and interrupted are the ones to trust. reworked catches real thrash and also catches a planned second edit, so read fifty of them before you trust it.

The Jev call

from typesafe_sdk import Choice, Noul, TypeSafeClient

client = TypeSafeClient()
MODEL = "jev-1.13.0"          # pin it; thresholds are tuned against a version

def judge(row):
    return client.system_one(
        model=MODEL,
        state={
            "goal": next((t["text"] for t in reversed(row["context"])
                          if t["role"] == "user"), ""),
            "recent_turns": row["context"],
            "proposed_tool": row["tool"],
            "proposed_input": row["input"],
            "repo": row["cwd"],
        },
        questions={
            "right_next_action": Choice(
                instructions="Given the goal and what has happened, what should the agent do next",
                criteria={
                    "read_more":  "Read or search more of the code before changing anything",
                    "edit":       "Make the change; enough is known",
                    "run_tests":  "Run the tests or the build to see the current state",
                    "ask_user":   "Stop and ask; the request is ambiguous or the choice is theirs",
                    "finish":     "The work is done and should be handed back",
                },
            ),
            "enough_context": Noul(
                instructions="The agent has read enough of the relevant files to make this change safely"),
            "destructive": Noul(
                instructions="This action can destroy work that is not recoverable from git"),
            "needs_verification": Noul(
                instructions="This change should be checked by a test or a build before the turn ends"),
        },
    ).answers

def to_row(row, a):
    return {
        **{k: row[k] for k in ("session", "uuid", "tool", "ts", "branch")},
        "actual": row["tool"],
        "jev_action": a["right_next_action"].choice,
        "jev_conf": a["right_next_action"].confidence,
        "p_enough_context": a["enough_context"].noul,
        "p_destructive": a["destructive"].noul,
        "p_needs_verification": a["needs_verification"].noul,
        "outcome": row["outcome"],
    }

What comes out

Map each real tool to the same five buckets — Read, Grep and Glob to read_more, Edit and Write to edit, Bash running a test to run_tests — and you have two products from one pass.

  1. A calibration curve on your own work. Bucket p_needs_verification by tenths and compare each bucket against the share of rows labeled failed. If the 0.9 bucket fails 30% of the time, Jev is not calibrated for this task and no threshold will save you.
  2. The disagreement set. Rows where jev_action != actual and the outcome was failed or interrupted. That is the counterfactual file you were after: the state, what the agent did, what a second opinion said, and evidence the agent was wrong. It feeds an eval suite, a few-shot set, or a fine-tune.

Cost check before you start. A decision point with six turns of context runs maybe 6,000 tokens. Ten thousand of them is 60 million tokens, which at $0.042 per million is $2.52 for the whole corpus. The extraction takes longer than the inference.

The live version follows from the offline one. Once the disagreement set shows where Jev is right and the agent is wrong, the same four questions go in a PreToolUse hook, the command Claude Code runs before every tool call: block when p_destructive > 0.8, warn when enough_context is under 0.3. That is jev-guard, built on your own thresholds instead of somebody else's.

Build idea 2: give swe-router a typed judgment

Your idea, worked out

The swe-router skill in vend/ already splits in two. route.py does arithmetic over models.json — 18 models, 21 tasks, scores by complexity tier, cost per task, a 3-point noise band. That half is deterministic and testable. The other half asks a frontier model to read the repo and place the task in one of four tiers, trivial to high. It then sets a floor of 55, 65, 70 or 75 by judging what breaks if the change is wrong.

That second half is a System One job. It returns four values, it has no business generating text, and today it costs a slice of an Opus turn to produce a number that route.py then looks up in a table.

import json, subprocess
from typesafe_sdk import Choice, Noul, TypeSafeClient

FLOORS = {"prototype": 55, "internal": 65, "production": 70, "sensitive": 75}
client = TypeSafeClient()

def classify(task, repo_map, touched_paths):
    a = client.system_one(
        model="jev-1.13.0",
        state={"task": task, "repo_map": repo_map, "files": touched_paths},
        questions={
            "tier": Choice(
                instructions="How big is this change",
                criteria={
                    "trivial": "A docs page, one render condition, two config passthroughs",
                    "low":     "A default changed across a couple of files, one small feature",
                    "medium":  "A feature across several files, a config surface, a template rewrite",
                    "high":    "A subsystem: rate limiting, token storage, a new authenticated endpoint",
                },
            ),
            "consequence": Choice(
                instructions="What breaks if this change is wrong",
                criteria={
                    "prototype": "A spike or scratch script; nobody merges it",
                    "internal":  "An internal tool, a test fixture, a docs page; a human reads it first",
                    "production":"A production service or anything users touch",
                    "sensitive": "Auth, payments, data deletion, a security path",
                },
            ),
            "hinges_on_one_thing": Noul(
                instructions="The task turns on one exact detail: an API contract, a security "
                             "invariant, a portability trap, a version comparison"),
            "beyond_measured_range": Noul(
                instructions="The change spans several services, ports a language, "
                             "or rewrites a framework"),
        },
    ).answers

    floor = FLOORS[a["consequence"].choice]
    if a["hinges_on_one_thing"].noul > 0.6:
        floor += 5
    return a, a["tier"].choice, floor

def route(task, repo_map, touched_paths):
    a, tier, floor = classify(task, repo_map, touched_paths)

    if a["consequence"].confidence < 0.6:
        return ask_developer_one_question(a["consequence"].probabilities)
    if a["beyond_measured_range"].noul > 0.7:
        return recommend_strongest("the benchmark does not reach this far")

    out = subprocess.run(
        ["python3", "route.py", "--tier", tier, "--floor", str(floor)],
        capture_output=True, text=True, check=True,
    )
    return json.loads(out.stdout), a

Four things change, and each is worth having on its own.

  • The skill runs without a frontier model. Today it needs an agent to read the repo and form a view. With Jev doing that in 100 ms for a fraction of a cent, the router fits in a pre-commit hook, a CI gate, or a wrapper that picks the model before the agent starts.
  • The floor stops drifting. Prose judgment of "what breaks if this is wrong" varies between runs of the same model. A pinned Jev version with fixed criteria does not.
  • The confidence answers a question the skill already asks. SKILL.md says to ask the developer only when the repo does not settle it, and leaves that call to the agent. consequence.confidence < 0.6 is that rule as a number.
  • You get a second dataset. Log the probabilities beside the recommendation and the task outcome. After a hundred routed tasks you can ask whether the tasks routed to a cheaper model came back worse, which is the question the 21-task benchmark cannot answer on its own.

One caution, from your own SKILL.md. Jev cannot compare numbers, so keep every threshold in Python: the 3-point noise band, the margin_is_meaningful test, the completion counts. Ask Jev what kind of change this is, then let route.py turn that into a model.

Six more ideas

  1. Tool selection for the MCP Gateway Registry. A registry with hundreds of tools cannot put every schema in the context. One Choice over tool names with one-line criteria, run against the user's request, narrows it to five before the agent sees anything. The registry already holds the descriptions the criteria need.
  2. Context pruning for the harness. winnow's approach, applied inside the benchmark harness: judge each block of tool output for relevance, stub the rest. Then measure whether the 21-task scores move. A cheaper context that holds the score is a result worth publishing.
  3. Triage the benchmark judge. Judging six artifacts per task with gpt-5.6-sol at high reasoning effort is the expensive part of a benchmark run. Use Jev for the mechanical checks — did the patch touch the files the spec named, does the testing plan mention the changed paths — and save the frontier judge for the scoring that needs reading.
  4. Assignment feedback that arrives before the deadline. For the Georgetown course, a rubric as five Score questions over a submitted notebook returns a provisional read in under a second per student. Publish the rubric criteria as the assignment spec and the students can run it themselves.
  5. Log triage. jevlogs does this for OpenTelemetry: one noul per line for "this needs a human tonight". The same shape works for a CloudWatch stream in front of a pager.
  6. Self-hosted A/B. Stand up openjev-sglang on a model you already serve, run the same question set against both, and compare accuracy and cost per thousand decisions. That is a direct extension of the self-hosted-versus-Bedrock cost work in the benchmarks repo, applied to decisions instead of patches.
